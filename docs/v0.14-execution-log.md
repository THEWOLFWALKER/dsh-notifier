## S01 — Channel single-writer convergence

### Pre-state found on dev

Outbound and inbound channel mutations were already *mostly* converged by v0.12.1 / v0.13:

- both Native (`src/control-surface/service.mjs`) and the Advanced Console
  (`src/admin/api.mjs`) already delegated outbound writes to a single
  `createOutboundConfigService` (`channel:<type>:outbound`, canonical) in the production assembly;
- inbound writes already used one `createInboundChannelConfigPort`
  (`<type>:account`) shared by both adapters;
- connectivity test already went through the same injected `channelTest`.

What was missing: a single **application service** owning channel write/test orchestration. The
orchestration was duplicated between the two adapters, and `src/admin/api.mjs` still carried a
latent legacy writer (`admin:channel:<type>:outbound`, and a fallback inbound port) for callers
that inject no canonical service.

### Work done

Added `src/control-plane/channels.mjs` — `createChannelControlService({ outboundConfig, inboundConfig, channelTest, saveInbound, removeInbound })`.
It owns orchestration only (save/remove outbound, save/remove inbound, test); it wraps the two
existing authorities and never becomes one (I1). Inbound save normalizes a non-durable result
into a `storage-failed` error (I2/I16).

Wired:

- `src/index.mjs`: one `channelControl` instance injected into both `createControlSurfaceService`
  and `createAdminApi`.
- `src/control-surface/service.mjs`: `channels.save` / `channels.test` now call the shared service;
  it constructs an equivalent instance from legacy deps when none is injected (test/back-compat).
- `src/admin/api.mjs`: `putOutboundChannel` / `deleteOutboundChannel` / `testOutboundChannel`
  canonical branches call the shared service; error-code mapping (422/404/500, 501 for
  not-configured) preserved. The pre-v0.13 legacy branch (only reachable when no canonical service
  is injected) is unchanged.

Added tests: `test/channel-control-service-v014.test.mjs` (6 cases) —

1. Native and Admin share one writer → same canonical key, no legacy dual-write, alternating
   field-level writes do not stale-overwrite;
2. real filesystem persist failure (state file under a regular-file parent) → `storage-failed`,
   neither memory nor runtime publishes;
3. durable success + runtime apply failure → `saved:true`, `applied:false`, `restart-pending`,
   desired already on disk;
4. canonical beats legacy overlay on conflict;
5. inbound save converges on the same canonical port; persist failure → `storage-failed`;
6. test orchestration reads canonical raw only; unconfigured → `not-configured`.

### Authority / Mutation order / Failure semantics

- Authority: unchanged — outbound desired config stays in `outbound-config.mjs`; inbound config
  stays in `inbound/channel-config.mjs`. The new module is orchestration only.
- Mutation order: validate (in the authority) → durable commit → runtime apply → settlement result;
  unchanged, now reached through one entry.
- Failure semantics: persist failure publishes nothing and reports `storage-failed`; apply failure
  keeps desired and reports `restart-pending`. Not hidden (I16).

### Tests cannot detect / still assumed

- No real provider hot-apply: the runtime swap is exercised against `OutboundSource` only.
- The legacy `admin:channel:<type>:outbound` writer still exists for pre-v0.13 callers that inject
  no canonical service. Production never reaches it, but it remains a latent second write domain;
  recorded in `docs/v0.14-assumptions.md` (A-006) and left for the S12/S15 convergence pass.
- Inbound orchestration is shared through the port but the Native path enters via the service while
  Admin enters the port directly; both target the same instance.

## S02 — Members / Pairing shared service

### Pre-state found on dev

Member and pairing mutations were already single-authority at the domain level (identity
`src/inbound/identity.mjs`, pairing `src/inbound/pairing.mjs`), but the **orchestration** lived
entirely inside the Advanced Console adapter `src/admin/api.mjs`:

- `getMembers` / `putMember` / `deleteMember` / `confirmPendingMember` / `dismissPendingMember`
  directly called `identity.list/listPending/listActive/updateBinding/removeBinding/confirmPending/dismissPending`;
- `mintPairingCode` / `revokePairingCode` directly called `pairing.mint/revoke`;
- the last-owner guard (putMember downgrade / deleteMember), the pending→member promotion, and the
  member-key parsing (`parseMemberKey` / `memberKeyOf` / `resolveMemberRecord`) were adapter-local.

There was no shared application service between the (future) Native surface and Admin, so S06/S07
would otherwise have to re-implement the same orchestration — the I1/I9 duplicate-writer risk S01
closed for channels.

### Work done

Added `src/control-plane/members.mjs` — `createMembersControlService({ identity, pairing })`.
It owns orchestration only:

- members: `listMembers(channel?)`, `addMember({channel,accountId?,userId,label?,origin?})`,
  `updateMember(key, {label?,role?})`, `removeMember(key)` (incl. the last-owner guard);
- pending identities: `listPending(channel?)`, `addPending(...)`, `approvePending(key)`
  (pending→binding via identity's existing `confirmPending` single transaction), `removePending(key)`;
- pairing: `listPairingCodes()`, `mintPairingCode({origin,mintedBy,ttlMs,label})`,
  `revokePairingCode(id,{by})`, `redeemPairingCode(code, who)`;
- exported key helpers `parseMemberKey` / `memberKeyOf` / `MEMBER_KEY_HINT` (single source for the
  member-key shape now that the key is part of the service contract).

It wraps identity/pairing and never becomes a second authority (I1); it does not re-implement the
domain's fail-closed validation or write logic (I7). Every mutation returns the underlying domain's
normalized result; durable failure surfaces as `storage-failed`, never as success (I2/I16).

Wired:

- `src/index.mjs`: one `membersControl = createMembersControlService({ identity, pairing })` created
  at assembly scope (not admin-private) and injected into `createAdminApi` via the new
  `membersControl` option, so S06/S07 can reuse the same instance.
- `src/admin/api.mjs`: the seven member/pairing handlers above now **delegate** to the shared
  service. Presentation-level shape/`ApiError` mapping, the `auditGuard` call sites and warn text
  stay in the adapter; capability (501) checks use the service's predicates
  (`canUpdateMember` / `canRemoveMember` / `canConfirmPending` / `canDismissPending` /
  `canMintPairing` / `canRevokePairing`). When no `membersControl` is injected, the adapter
  constructs an equivalent service from its existing `identity`/`pairing` deps, so old tests and
  pre-v0.14 callers are unchanged.

Added tests: `test/members-control-service-v014.test.mjs` (6 cases) —

1. legal member write via the service lands on the identity authority (store key + read-back);
2. illegal identities (unknown channel / illegal accountId / empty or over-long userId) fail
   closed with zero disk or memory writes;
3. pending→member promotion is atomic — a forced-failure store leaves memory and disk unchanged and
   reports `storage-failed`;
4. real filesystem persist failure (state file under a regular-file parent) → `storage-failed`,
   never a false success;
5. returned views leak no credential/sensitive fields (member/pending/code projections match the
   admin `getMembers` redaction shape, and the code face never appears);
6. pairing mint/revoke and the owner-last guard are normalized through the service.

### Authority / Mutation order / Failure semantics

- Authority: unchanged — member identity stays in `identity.mjs`, pairing lifecycle stays in
  `pairing.mjs`. The new module is orchestration only (I1).
- Mutation order: validate (in the authority, fail-closed) → durable commit → result; the
  pending→member promotion reuses identity's single `store.transact` path (I3), so a failed
  transaction publishes neither memory nor disk.
- Failure semantics: durable failure is returned as `storage-failed` and never reported as success
  (I2/I16); illegal identities are rejected without any write (I7).

### Tests cannot detect / still assumed

- `confirmPendingMember` in the adapter still maps any non-`already-bound` failure (including a
  persistence failure) to HTTP 404 — preserved verbatim from pre-S02 to keep the HTTP contract
  unchanged, but it means a confirm persistence failure is still presented to the Console as
  "not found". The service itself reports `storage-failed` truthfully; the adapter mapping gap is
  recorded here and left for a later convergence pass (does not fake success).
- Capability predicates are grouped (`canUpdateMember`/`canRemoveMember`,
  `canConfirmPending`/`canDismissPending`); a hand-rolled partial identity mock exposing only one of
  a pair would 501 where the pre-S02 code might not. Production and all existing tests build a full
  identity, so this is a test-harness-only edge.
- No real device/provider: pairing redeem/lockout is exercised elsewhere; this stage covers the
  adapter-reachable orchestration only.

## S03 — Sessions / Routing shared service

### Pre-state found on dev

Session/routing orchestration lived entirely inside the Advanced Console adapter
`src/admin/api.mjs`:

- `overview` counted sessions by reading `route:sessions` directly and calling `registry.isActive`;
- `getBindings` / `putBindings` read/derived the two binding tables locally, and `putBindings`
  re-implemented the whole-table replacement by per-key `router.setAgentBinding` /
  `clearChannelDefault` calls (multi-key, non-transactional);
- `getSessions` assembled the projection (`route:sessions` + live `router.resolveOutbound` + the
  control-overlay summary) locally;
- `patchSession` / `patchSessionControl` called `router.setSessionOutbound` / `setSessionControl`
  directly, with adapter-local `hasSession` / `controlSummary`.

There was no shared application service, so the (future) Native Session / Advanced Bindings
surfaces (S08/S09) would have had to re-implement the same projection and write orchestration —
the same I1/I9 duplicate-writer risk S01/S02 closed for channels and members.

### Work done

Added `src/control-plane/sessions.mjs` — `createRoutingControlService({ router, registry, store, warn })`.
It owns orchestration / projection only and composes the three existing routing authorities
(it never merges them, I1):

- session lifecycle stays in `src/routing/session-registry.mjs`;
- routing / outbound overrides stay in `src/routing/agent-router.mjs`;
- control-overlay normalization stays in `src/control/session-arbiter.mjs`.

Methods: `bindingsSnapshot()`, `replaceBindings({ agents?, channels? })`, `sessionIds()`,
`hasSession(id)`, `resolveOutbound(...)`, `sessionsView({ enabledTypes })`,
`patchSessionOutbound(id, diff)`, `patchSessionControl(id, diff)`; plus the exported
`controlSummary(control)` redaction helper (single source for the safe overlay summary).

Crucially the projection does **not** reintroduce the historical `route:sessions` whole-table
stale-cache overwrite: every write goes through the router setters, which re-read the latest store
table and merge the field-level diff (I10, anti sibling-clobber). A failed durable commit is
surfaced as `storage-failed`; the adapters must report failure, never success (I2/I16).

Domain primitive added in `src/routing/agent-router.mjs` (v0.14 S03):

- `snapshotBindings()` — copy-on-read snapshot of both binding tables;
- `replaceBindings({ agents, channels })` — when both sides are supplied and the store has
  `transact`, the two tables are committed in a **single transaction** (`transactDurable`, I3):
  either both land or neither does. A single side degrades to the existing single-key atomic write;
  a legacy store without `transact` degrades to two single-key writes but returns an honest
  `ok:false` on any failure — never a half-committed success.

The whole-table normalization (`normalizeAgentsTable` / `normalizeChannelDefaultsTable`) was
extracted from the pre-existing `replaceAgentBindings` / `replaceChannelDefaults` into reusable
pure functions so the one-shot double-table path validates exactly like the per-table paths.

Wired:

- `src/admin/api.mjs`: `overview` / `getBindings` / `putBindings` / `getSessions` / `patchSession` /
  `patchSessionControl` now **delegate** to the shared service (injected as `routingControl` at
  assembly scope; otherwise constructed from the adapter's existing `router`/`registry`/`store`).
  Request-shape validation, `ApiError` mapping (422/404/500) and the `auditGuard` call sites stay in
  the adapter. The now-unused adapter-local `readTable` / `registrySessionOf` / `callSetter` helpers
  and the `route:*` key constants were removed (no dead double-read path left behind).

Added tests: `test/routing-control-service-v014.test.mjs` (6 cases) —

1. Native and Admin share one service → both binding tables land on the canonical
   `route:agents` / `route:channels` keys; `service.bindingsSnapshot()`, `admin.getBindings()` and
   a service-side single-table replace all read/write the same facts (no second cache);
2. two-table replacement commits in **one** `store.transact` call (`calls === 1`); a
   persist-failing store leaves both tables absent and reports `storage-failed` — no half commit;
3. an invalid whole-table shape is normalized to `invalid` by the service with zero writes;
4. the session list projection equals canonical table + live resolution + redacted control summary
   (active-first ordering, corrupt rows skipped, `owner` / member identifiers never leak);
5. session outbound/control overlays are written through the service with field-level diffs that do
   not clobber siblings, and unknown sessions still 404;
6. a real filesystem persist failure surfaces truthfully (binding replace `ok:false`; adapter
   500s) with no false success.

### Authority / Mutation order / Failure semantics

- Authority: unchanged — routing/outbound overrides stay in `agent-router.mjs`, session lifecycle
  in `session-registry.mjs`, control overlay normalization in `session-arbiter.mjs`. The new module
  is orchestration/projection only (I1).
- Mutation order: validate (adapter 422 / router shape) → durable commit → projection read-back;
  the two-table path is one transaction (I3); the session/overlay paths re-read + merge before write
  (I10).
- Failure semantics: a failed durable commit publishes nothing and is reported as `storage-failed`
  / HTTP 500; never hidden, never a false success (I2/I16).

### Tests cannot detect / still assumed

- No real DSH host round-trip in this stage: the projection and write orchestration are exercised
  against the real router/store + a registry stub only; the Native surfaces that will consume the
  service arrive in S08/S09.
- The Advanced Console's per-key legacy behaviour for a caller that injects no router is preserved
  (the service reports `not-supported`); production always injects the shared router.
- `controlSummary` intentionally exposes only derived booleans / counts; the canonical raw overlay
  (with the original owner / members) is stored but never projected — this is the same redaction the
  pre-S03 adapter performed.
