# 开发与用户视角的设计复盘

这是对既有实现及本 taskpack 自身的批判性检查。优先按用户任务和真实故障后果取舍，不按 201 条数量驱动重构。

## 1. 现有产品设计里最不合理的部分

| 判断 | 用户代价 | 开发代价 | 决策 |
|---|---|---|---|
| 以“有凭证”推导“已授权开启私聊” | 通知配置可意外开放控制；关闭后 UI 与现实不一致 | 期望配置、transport、准入三套状态纠缠 | 明确授权状态是唯一权威；只有显式开启可入站，关闭先撤权再停 transport |
| 把失败投影为空/成功 | 无法分辨未配置、读失败、投递未知；用户会反复操作 | 测试只验证 happy path，故障源被隐藏 | Read model 有 unavailable/stale；发送有具体 evidence；DOM 按真实错误路径验收 |
| “稍后处理”执行终态拒绝 | 用户以为以后还能处理，实际丢问题 | 文案和状态机互相矛盾 | 优先实现真 defer；若提醒与重现成本过高，则改成准确的“拒绝”，绝不假称稍后 |
| 管理能力在后端但 UI 无入口 | 成员、配对码无法自助管理 | 多套死 API/allowlist 形成审计负担 | Native 完成真正需要的日常能力，其余删除；旧控制台整套删除 |
| 28 渠道广度与用户体验质量不匹配 | 长列表截断，某些协议无真机证据；“支持”含义不一 | 每个 provider 均有生命周期和外部变更成本 | 设 `verified / limited / experimental` 的内部发布矩阵，UI 只把可证明能力作为可用承诺；不盲目增加渠道 |
| Cloud 一键体验只隐藏术语，未隐藏真实复杂度 | 可能无感创建公网端点、资源/费用，故障难自救 | 动态安装 CLI、云状态恢复与本地 runtime 紧耦合 | 一键仍要说明账号授权、公开地址和资源后果；技术词藏进诊断。优先可复现安装与幂等资源清单，减少运行时下载 |
| 旧控制台退出不彻底 | 两套入口让用户不知道去哪里 | 死代码可被误接回，安全面仍在 | 在 Native/离线恢复路径可用后删除整套旧控制台；最小只读恢复如确需则新设计 |

## 2. 本规划原先也有需要收紧的设计

1. **UX 不能等到 S3。** S0 就冻结用户旅程、词汇和错误状态；S1 的“关闭私聊”、S2 的“投递未知/Cloud 恢复”必须各自交付真实 Native 纵向切片。S3 只做整体 IA、可发现性、视觉和删旧代码的收尾。
2. **B0 的“60 条”只是索引，不是 60 个独立发布关卡。** 实际 gate 按根因与用户能力定义。一个安全不变量可覆盖多个 ID；缺真机证据会阻断对应能力的公开声明，而不必让不相关能力无限等待。
3. **撤销顺序需防重启回开。** 当前进程先设置同步 admission deny；在同一操作内持久化新的 deny generation/关闭意图；只有落盘成功才回“已关闭”。然后 abort 和 drain transport。落盘失败时当前进程仍 deny，UI 显示“关闭未完成”；启动时对无效/不完整授权默认 deny。单纯先停 transport 后写 desired off 不足以保证重启后的权限状态。
4. **Cloud 错误不能只按异常名字分类。** `credential-changed` 若发生在远端请求之前可进入 failed；若远端操作已开始且结果不明，则即使随后发现凭证变化也必须 recovery-required。判定依据是 checkpoint 和外部副作用边界，不是错误码本身。
5. **公共结果不宜再让 `ok` 承载多重意义。** 首选 `{evidence, retryAdvice, ...}` 作为唯一控制依据。若当前正式外部消费者确需 `ok`，则定义它只表示“调用取得正向 provider 证据”，明确 accepted 仍非送达；测试禁止仅凭 `ok` 自动重试。
6. **不要为小样本旧状态建设长期迁移框架。** S0 只读盘点，备份旧状态、停用旧权限并让用户重新配置，给出短而清楚的步骤；不做自动转换。
7. **不要把同一套状态枚举泛化到所有域。** DeliveryEvidence 只描述通知/消息发送。Cloud Job、私聊准入、Native 读取各有独立状态机；UI 汇总可共用展示原则，但不共用含糊的 `status:ok`。
8. **dsh-im 对齐只对真实用户价值和真实契约。** 若 `dshIm.*` 没有 Native 用户任务，删除 daily surface；bridge 是否保留需有明确当前消费者。不能一边声称对齐、一边只由错误 mock 证明功能。上游目前 checked v1 首版只支持 Feishu/Lark，不应把桥的存在等同所有渠道可用。
9. **Store 效能问题要定量。** 保持事务权威与复制边界；记录 state 大小和 p95/p99 event-loop delay 后再决定拆分、批处理或 worker，避免为了“async 化”引入更多一致性问题。

## 3. 建议的产品验收指标

- 通知单独配置后私聊 transport 启动次数为 0；私聊关闭确认后，新指令准入次数为 0，重启后仍为 0。
- 首次开通知、开私聊、确认身份、选任务、处理问题、关闭私聊六个任务都能从 Native 完成，无需打开诊断入口。
- 异常读、未知发送、部分 Cloud 操作三类状态，用户能在界面判断“发生了什么、是否应重试、下一步去哪”；不得显示空配置或成功式标题。
- 多 owner、超过 12 渠道、超过 20 待办、超过 10 任务时，用户仍能找到并操作目标，计数真实。
- 能力矩阵按渠道记录 `tested local / upstream contract / real provider / real device` 四层证据；缺哪层标 unknown，不能以绿色测试数填充。
