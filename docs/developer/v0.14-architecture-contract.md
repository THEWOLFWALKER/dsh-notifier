# dsh-notifier v0.14 Architecture Contract & Invariants

Status: frozen at S00 of the v0.14 Native-first Completion workstream.
Branch: `dev` only (see execution log).

This file is the highest-priority architecture constraint for the v0.14 workstream. When an
implementation detail conflicts with it, fix the implementation. Do not silently weaken an
invariant.

Source task pack: `dsh-notifier v0.14 Native-first Completion` (S00–S15). This document
restates its contract in repository terms and points at the actual modules that hold each
authority. It does **not** change runtime behavior; S00 is documentation-only.

---

## 1. Product target (one line)

> Move dsh-notifier from "it has a Native UI" to "users almost never need to leave DSH except
> for Recovery / deep diagnostics."

v0.14 also formally defines, for the first time, the compatibility boundary:

> **Protect user data and the upgrade path. Do not promise permanent maintenance of old
> product shapes (old UI / old internal write forms).**

Native and Advanced Console are adapters. Neither is a new business authority.

```text
                 ┌─ DSH Native UI (default daily entry)
                 │
Shared Control ──┼─ Advanced Console (Recovery / deep diagnostics)
Services         │
                 └─ CLI / automation adapters (where existing capability requires it)
        │
        ├─ identity / pairing
        ├─ agent-router / session-registry / session-arbiter
        ├─ questions / control core
        ├─ outbound config / runtime source
        ├─ health / activity / ledger
        └─ transactional store
```

---

## 2. Supported upgrade boundary

Formally supported upgrade paths:

- `v0.12.x -> v0.14`
- `v0.13.x -> v0.14`

Must be preserved across those paths:

- channel config
- member identity
- pairing / pending state (within its legal TTL / lifecycle)
- bindings
- sessions
- route / control overlay
- question / control durable state
- credentials / secrets
- existing ledger / audit security boundary

Older versions (v0.11 and earlier) are **best-effort migration input only**. We do not promise
their old UI, old API, old restart semantics, or old internal keys remain writable.

Legacy keys may continue to be **read** as a migration source. New writes must enter the
canonical authority.

```text
legacy input ──migrate──> canonical state
                       └─> runtime

Forbidden: writing canonical and then also writing legacy, creating two authorities.
```

Legacy cleanup is not required to happen automatically in v0.14; a read-only compatibility
window is safer. Existing legacy surfaces in this repo include
`src/control-surface/channel-config-migration.mjs` (channel config) and the one-time
`inbound.allowUsers` YAML migration input.

## 3. Invariants

### I1 — One business fact, one authority

Projections / caches / view models may be plural; the **writer authority** is single.

| Fact | Authority (module) |
|---|---|
| outbound desired config | canonical outbound config service (`src/control-surface/outbound-config.mjs`) |
| outbound applied runtime | OutboundSource / runtime holder (`src/assembly/outbound.mjs`) |
| channel health | health observer (`src/control-surface/health.mjs`) |
| member identity | identity (`src/inbound/identity.mjs`) |
| pairing lifecycle | pairing (`src/inbound/pairing.mjs`) |
| session lifecycle | session-registry (`src/routing/session-registry.mjs`) |
| routing / outbound overrides | agent-router (`src/routing/agent-router.mjs`) |
| session policy normalization | session-arbiter (`src/control/session-arbiter.mjs`) |
| question settlement | questions / control settlement path (`src/questions/router.mjs`, `src/control/contract.mjs`) |
| Native refresh cursor | surface revision `{epoch, revision}` (`src/control-surface/revision.mjs`) |

The store (`src/inbound/store.mjs`) is a durability primitive, **not** a business authority.

### I2 — Durable commit and runtime apply are layered

Durable commit failure:

```text
memory(authority) == before
disk == before
runtime == before
UI/API must not report success
```

Durable commit success but runtime apply failure:

```text
desired/disk = after
runtime = before / failed
applied = false
restartPending / apply error exposed explicitly
```

It is forbidden to secretly roll back an already durable-committed user config "to look
consistent".

### I3 — Multi-key durable business actions are atomic

If a business action semantically modifies multiple durable keys at once: all commit or none
happen. Prefer `store.transact()` or a domain-owned transaction.

Application services must not call several setters in sequence and then "best-effort
rollback". External provider side effects cannot be ACID — use the I5 claim protocol instead.

### I4 — State semantics are not mergeable

```text
configured
!= enabled
!= active
!= healthy
!= accepted
!= delivered
!= rendered
!= settled
```

A provider HTTP 2xx / messageId does not imply the real device received anything, and still
less that interactive buttons work. UI must not collapse these levels into one `ok` boolean.

### I5 — Irreversible side effects require a durable claim first

For side effects that may repeat with real impact:

- approval / question settlement
- stop / remote action
- single-use callbacks
- external actions requiring exactly-once / first-wins

Order:

```text
validate
-> durable claim
-> irreversible effect
-> durable settle/reconcile
```

When the claim fails, the effect must not execute.

### I6 — Process-local monotonic state carries an epoch

Revision / cursor / generation / counter that is only monotonic within one process must carry
a boot epoch or equivalent incarnation id. `revision=100` and a new process `revision=1` must
not be compared bare. The Native `{epoch, revision}` model
(`src/control-surface/revision.mjs`) is kept.

### I7 — Security-relevant capability defaults to fail-closed

Inputs / capabilities:

- secret
- token / webhook
- network destination / private network
- principal / identity
- accountId / userId / chatId
- group control
- file URL / attachment
- callback source
- unknown provider

New fields / unknown shapes / unknown capabilities must not be auto-allowed just because no
deny flag was written. Mutation payloads should reject unknown security-relevant fields rather
than silently accept them.

### I8 — Every process-local resource has capacity and a lifecycle

Not only Map/Set, but also queues, inflight promises, timers, debounce/grace pools, waiters,
SSE/socket clients, callback refs, caches, abort listeners, reconnect state.

Each resource must answer: owner? max capacity? TTL / eviction? dispose cleanup? abort
cleanup? restart behavior?

### I9 — Presentation is never the business authority

Native / Admin / CLI may only:

```text
validate presentation-level shape
-> call shared control service
-> render the returned canonical result
```

They must not directly operate a business state table.

### I10 — Every read-modify-write declares a concurrency model

If the shape:

```text
read whole table
modify one field
write whole table
```

appears, the code must state and verify what happens when another writer modifies a sibling
field concurrently.

Allowed approaches: single writer; transactional mutation; field-level setter; fresh re-read
+ conflict handling; CAS / revision. Stale-cache whole-table overwrite is forbidden.

(This is the exact class of the historical `route:sessions` stale-cache overwrite incident.)

### I11 — Desired / Applied / Observed are three truths

```text
Desired  = durable config
Applied  = runtime loaded config/state
Observed = provider / runtime recent observation
```

Diagnostics and UI must know which layer they display.

### I12 — Migration is idempotent, one-way, conservative

Each migration:

- repeated run == no extra effect
- canonical wins over legacy
- failure does not delete legacy
- old values are not cleaned before success
- corrupt / unreadable state is not treated as a fresh install
- migration does not secretly trigger network side effects

### I13 — Host seams are traceable to official source

Each Host integration must record: seam name, official source path, verified DSH versions,
capability probe, fallback, failure mode, test / evidence level.

It is forbidden to declare a Host API exists from old issues, old comments, a competitor shim,
or model memory.

### I14 — Capability detection beats version guessing — but detection also has a contract

Correct:

```text
known version evidence
+ feature probe
+ expected shape validation
```

Wrong:

```text
if version >= x => support everything
if ctx.foo => all foo capabilities true
```

### I15 — Evidence level can never be upgraded by wording

```text
unit-tested
contract-tested
source-verified
host-smoke-verified
provider-verified
real-device-verified
external-evidence-pending
```

A lower level cannot be advertised as a higher one. Promotional words such as
`supported / works / healthy / delivered` must not silently substitute for an evidence level.

### I16 — Mutation errors are not hidden state transitions

Mutations must distinguish at least: validation failure; conflict / busy; persistence failure;
runtime apply failure; unsupported capability; provider failure.

Queries / diagnostics may degrade locally; mutations must never `catch {}` and return success.

| Diagnostics | **no new authority** | none (projection only) (S10) | Native / Admin report |

## 5. Dependency direction

```text
client.js
   ↓ RPC
src/control-surface/service.mjs  ───────┐
                                        ↓
src/admin/api.mjs ───────────────> control-plane/*
                                        ↓
                              domain authorities
                                        ↓
                                     store (src/inbound/store.mjs)
```

Reverse imports are forbidden. A control-plane service must not import `client.js`, the Admin
UI, or an HTTP server, and must not hold a second cache truth.

---

## 6. Transaction rule

If a shared service finds that an underlying action needs multiple keys and the domain has no
atomic primitive:

1. do not chain multiple setters inside the service;
2. add one minimal transactional method to the **domain module that owns those keys**;
3. prove with a real store-failure test that failure publishes neither disk nor memory;
4. then have the service call that method.

---

## 7. Real-device / provider verification is non-blocking

The unattended environment generally has no QQ / Feishu / DingTalk real device and no real
credentials. Therefore:

- real-device / real-provider verification is **not** a stage-completion gate for this workstream;
- missing real credentials must never be faked as passing;
- contract / mock results must not be re-described as real-device evidence;
- incomplete items are recorded in `docs/developer/v0.14-evidence-matrix.md` as `external-evidence-pending`;
- if an independent environment happens to have real Host smoke ability, it may be run and
  recorded, but a failure only blocks when it can be proven to be a regression of this stage's code.

QQ issue #26 and the other open device/provider items keep their evidence boundary and must not
be auto-closed for v0.14.

## 8. Non-goals for v0.14

- no new provider channels (the 29th/30th are out of scope; focus is control-plane completeness)
- no large directory refactor
- no deletion of Advanced Console (frozen as a Recovery adapter only)
- no Native → localhost Advanced Console API calls
- no copying of Members / Sessions / Questions business logic into `client.js`
- no `>=`/`^` widening of the DSH peer range
- no treating dsh-im compatibility shims as an official DSH contract
- no provider adapter rewrite for the sake of Native migration
- no real provider / device verification as a mandatory gate
- no change to business state semantics for the sake of UI uniformity
- no store / routing / session-registry rewrite
- no `main` / release / npm publish
