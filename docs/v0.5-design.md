# dsh-notifier v0.5 设计稿：移动指挥中心 + 通知动作闭环

> 状态：待审批（架构审查已完成三轮 + 基线验证，见文末审查记录；实施前基线 625 测试全绿）
> 原则延续：零运行时依赖、零构建、克制不过度实现、存量行为默认不变（本版两处默认值变更见 §8）。

## 0. 目标与非目标

**目标**：人离开桌面后，用手机完成「看状态 → 判断 → 处置」的完整闭环。

1. **状态上报线**：任务开始（opt-in）、长任务心跳、疑似卡住三类事件通知——移动端实时掌握 agent 在干什么。
2. **通知动作闭环**：通知不再只是「看」，可点按钮直接处置（v0.5 仅一个动作：停止任务；架构上可扩展）。
3. **移动命令中心补全**：既有 `/` 命令族即命令中心，补 `/quiet`（通知疲劳管理）。
4. **管理台移动端适配**：响应式 CSS（P2）。

**非目标（明确不做）**：

- `/retry`：宿主 Agent API 无 retry 语义，`followup("继续")` 不可靠——不做，记入决策。
- 审批线迁移到 ActionDispatcher：审批工作正常，v0.5 只并行新增动作线，避免重构既有稳定路径。
- 浏览器通知按钮（Notification.actions 需 Service Worker）/桌面通知按钮（osascript 无交互回调）：不做，浏览器通知已带「打开管理台」隐含路径，聊天通道按钮已覆盖移动端。
- 任意自定义动作（用户配置 handler）：违背「入站永不执行任意代码」军规，动作只限内置白名单。

## 2. 特性 A：状态上报线

### 2.1 新模块 `src/status/turn-tracker.mjs`（纯逻辑，~120 行）

对齐 `createGraceQueue` 模式：可注入 `now/setTimeout/clearTimeout`，全防御，永不抛出。

```
状态：Map<sessionId, { turn, startedAt, lastEventAt, heartbeatTimer, stallTimer, stallFired }>
observe(session, event)：
  - 'turn/start'        → 建档（upsert，重置计时）；装心跳/卡住定时器
  - 'turn/end'          → 清档清定时器（不在此发通知——turn/end 通知走既有 intent 线）
  - 其它一切事件         → 刷新 lastEventAt；stallFired=false；重装卡住定时器
                          （user/* 例外：不刷新——用户打字不等于 agent 有进展；
                            未知类型按活跃处理——宁可少报卡住，不可误报）
  - 'agent/disposed'    → 清该会话档（经 observeAgentDisposed，装配层接线）
心跳：首跳 startedAt + firstAfterMs，此后每 everyMs；触发回调 onHeartbeat(session, {elapsedMs, idleMs})
卡住：lastEventAt + afterMs 触发，每个「静默期」只报一次（下次活跃后重装可再报）
上限：MAX_TRACKED = 32，超限淘汰 lastEventAt 最旧者（防泄漏，防御性）
dispose()：清全部定时器
```

三配置全关时 tracker 不建定时器（observe 空转 O(1)）。

### 2.2 event-listener 接线

```
sessionListener(session, event)：
  tracker.observe(session, event)   // ① 永远最先喂 tracker（独立于 intent 过滤——
                                    //    events.turnEnd 关闭或未知 reason.kind 时清档仍需发生）
  if user/* → grace.activity(); return   // ② 既有逻辑不变
  intent 映射 → eventAllowed → dedup → debounce/grace → push   // ③ 既有逻辑不变
```

新增 intent：

| intent | 触发 | level | 延迟管线 | 默认 |
|---|---|---|---|---|
| `turn/start` 🚀 任务开始 | turn/start 事件 | passive | 与 turn/end 同管线（debounce→grace） | **关**（桌面场景每 turn 一条是噪音） |
| `longRunning` ⏱ 任务进行中 | tracker 心跳回调 | passive | 直推（自身已按间隔限频） | **开**（firstAfter 15min，仅长任务触发） |
| `stall` ⚠️ 疑似卡住 | tracker 卡住回调 | timeSensitive | 直推（等人决策类，同 approval/agentError 不进宽限窗） | **开**（10min 无事件） |

**turn/start 的合并语义（已验证）**：`createTrailingDebounce.schedule` 对同 key 是「替换 pending + 重置定时器」——turn/start 挂入 debounce 后若 10s 内同会话 turn/end 到来，后者替换前者，只发「任务完成」一条。快速连续 turn 同理合并。subagent 会话也在 firehose 内：卡住/心跳对 subagent 同样有价值（卡住的 subagent = 卡住的任务）；turn/start 开启时 subagent 噪音由 debounce 合并 + 文档说明适用场景兜住。

**文案**（turn/start 详情 = workspace 名；心跳附 `lastAssistantText` 尾部 ≤200 字符摘录）：

```
🚀 任务开始 | <workspace>
⏱ 任务进行中 | <workspace> / <sid 前 8 位>
   已运行 23m，最近活动 40s 前
   （最近输出摘录…）
⚠️ 疑似卡住 | <workspace> / <sid 前 8 位>
   已运行 12m，最近活动 10m 前
   （长工具执行可能误报；回复 /stop 取消，或调 events.stall.afterMs）
```

心跳与卡住通知尾部统一附 hint：「回复 /stop 取消」——这是全通道兜底动作路径（与审批「回复 1/2」降级同构）。

### 2.3 配置面（config.mjs events 块扩展，归一后新增三键）

```yaml
events:
  turnStart:  { enabled: false }
  longRunning: { enabled: true, firstAfterMs: 900000, everyMs: 900000 }
  stall:      { enabled: true, afterMs: 600000 }
```

归一军规（吸取 v0.3.2 mergeWindowMs 教训）：数值统一 `Math.max(60_000, Number(x) || 默认)`——下限钳制 60s，杜绝误配 0/小值刷屏；语义歧义（0 = 关？）不存在，关闭一律 `enabled: false`。

## 3. 特性 B：通知动作闭环

### 3.1 新模块 `src/actions.mjs`（~100 行）

```
createActionDispatcher({ vault, store, logger })
  register(kind, handler)                     // handler({ actionKey, payload }) -> { ok, message }
  mintAction(kind, payload) -> { key, token } // key = `act:<sessionId>:<rand4hex>`（跨重启唯一）；
                                              // 账本行 { kind, payload, status:'pending', createdAt } 写 store
  dispatch({ actionKey, token, via, userId }) -> { ok, reason?, message }
      ① vault.verify(token) + key 匹配 → malformed / bad-signature / expired
      ② 账本首达：非 pending → already-resolved
      ③ handler 缺失 → unknown-kind（先落 resolved 防重试风暴）
      ④ handler 异常 → action-failed + 中文反馈（绝不向上抛）
  dispose()
```

内置动作（装配层注册，仅此一个）：`turn/cancel`——`ctx.agents.get(payload.sessionId)?.cancel('remote-action')`，权限面与 `/stop` 完全等价。

**安全模型**（与审批同一信任链，零新增信任假设）：

- 按钮真实性：通道回调本身（bot 私聊 / 卡片操作者）——审批按钮已依赖并验证此链；
- token：HMAC + TTL 默认 10min（过期卡片点击 → 「已过期」终态文案）+ 账本单次核销；
- 动作白名单：只有内置 handler，永无任意代码执行（军规延续）。

### 3.2 契约扩展 `src/inbound/_contract.mjs`

- 新导出 `buildActionPayload(actionKey, token)` → `ac:<actionKey>:<token>`；`parseActionPayload(data)`（与 parseApprovalAction 同构解析：首段 `ac`、末段 token、中间归 key——key 含冒号安全）。
- `normalizeInbound` 增加可选方法归一：

```
async sendActionCard({ chatId, title, content, actions: [{ label, data }] }) -> { messageId } | null
```

归一层按「方法存在与否」判定，与新旧形状无关：P1b 会在 telegram-bot.mjs（旧形状）与 feishu-bot.mjs（新形状）各实现一个；任何未实现该方法的通道实例（含第三方按旧契约实现的 inbound）→ 恒 null（调用方降级文本 hint）；capabilities 不动。

### 3.3 通道实现（仅 telegram + feishu，各约 30 行；qq/wxpusher/wechat/dingtalk 零改动）

- telegram：`sendActionCard` = sendMessage + inline_keyboard（actions → 按钮，callback_data = data）；回调分支 `parts[0] === 'ac'` → `actions.dispatch(...)` → answerCallbackQuery(result.message) + editMessageText 终态。
- feishu：`sendActionCard` = 现有卡片构建风格 + 按钮 `value.act = payload`；`card.action.trigger` 回调加 `parseActionPayload` 分支 → dispatch → toast + patch 卡片终态（不 await，3s 军规不变）。
- 通道创建参数增加可空 `actions`（缺省 → `ac:` 分支不存在，行为与 v0.4.0 逐字节一致）。

### 3.4 推送路径（event-listener wiring 增加可选项）

```
wiring: { router?, registry?, actions?, interactive? }   // 后两者新增，全可选、惰性求值（见 §6）
push(intent, session, actionSpec?)：
  ① notifyAll(文本含「回复 /stop 取消」hint)      // 既有出站分流（channelTypes/quiet）照旧
  ② 若 actionSpec && actions() && interactive()：
     mintAction('turn/cancel', { sessionId }) → 对每个交互通道 notifyTargets() 发 sendActionCard
     （interactive 传原始实例列表，push 侧 normalizeInbound 防御归一——stall/心跳触发频率低，归一开销可忽略；
       尽力而为：单通道失败只 warn；卡片是增强 UX，文本 hint 是兜底）
```

stall 与 longRunning 通知携带 `actionSpec = [{ kind:'turn/cancel', label:'⏹ 停止任务', payload:{sessionId} }]`；其余通知不带。

**顺带收益（零成本）**：stall/longRunning 走 notifyAll → `onSend` → v0.4.0 事件 hub → 管理台 SSE → 浏览器系统通知，自动出现在浏览器通知页（含移动端浏览器）——无需任何额外接线。

## 6. 装配顺序（index.mjs）——架构审查修正稿

**审查发现**：`createEventListener` 现装配于 inbound 栈**之前**（index.mjs 第 177 行），而 vault/bus/交互通道都在白名单块内（第 284 行起）才创建——「wiring 直接注入 actions/interactive 实例」在时序上不可行（审查第一轮后修正，原稿假设了错误顺序）。

**方案：惰性 getter（零装配顺序变更，仓库既有先例）**——`registerNotifyTool` 的 `channelTypes: () => resolved.channels.map(...)` 即同一模式：

```
let actionsRef = null
let interactiveRaw = []            // 与 approval 共用的 interactiveInstances 引用
disposers.push(createEventListener(ctx, notifier, resolved, {
  router, registry,
  actions: () => actionsRef,       // 惰性求值：stall/心跳触发时（装配早已完成）才解引用
  interactive: () => interactiveRaw,
}))
// —— 白名单块内（既有代码位置）——
const vault = createTokenVault(...)         // 既有
const bus = createInboundBus(...)           // 既有
const actions = createActionDispatcher({ vault, store, logger })
actions.register('turn/cancel', ...)        // ctx.agents.get(sessionId)?.cancel('remote-action')
actionsRef = actions                        // 赋值在 telegram/feishu 创建之前即可（注入通道用）
interactiveRaw = interactiveInstances       // 通道全部挂载后赋值（push 侧每次 normalize 防御）
telegram/feishu 创建参数增加 actions（可空）
disposers.push(() => actions.dispose())
```

**降级闭环**：未配置任何 inbound（白名单空）→ actions 永不创建 → `actionsRef` 恒 null → 通知文本 hint 仍全通道可达，动作卡片自然缺席——与「无 inbound 时行为不变」兼容红线自洽。

dispose 聚合：eventListener 清理内含 tracker.dispose；actions.dispose 在白名单块内随 disposers 聚合。

## 8. 兼容性影响

- **默认值变更两处（0.x minor 允许，CHANGELOG 显著标注）**：stall、longRunning 默认开——仅 10min+ 卡住 / 15min+ 长任务触发，低噪高值，均可一行配置关闭；存量「零配置」用户的通知流会新增这两类（以往完全静默的长任务从此有信号——这是版本主题，非回归）。
- turnStart 默认关 → 未显式开启者通知流零变化。
- 契约：sendActionCard 可选、actions 注入可空 → 六通道中四通道零改动；telegram/feishu 缺省注入时行为逐字节不变。
- 既有测试零破坏目标：events 归一新键带默认值；tracker 在既有事件路径上无副作用。
